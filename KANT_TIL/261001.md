- LangChain9-1
  - 여러 실패에서 재시도를 할 수 있지만 재시도를 하더라도 성공할 수 없는 실패와 가능한 실패를 구분해야 한다.
  - 질문이 비어있거나 자료형이 잘못되거나 타입에러같은 것들은 아무리 반복을 해도 오류가 발생한다.
  - 일시적인 모델 연결 실패, 순간적인 서버 과부하는 대기하면 성공할 수 있기 때문에 재시도하기에 적합하다.
  - `with_retry`를 통해서 재시도 설정을 할 수 있으며, `retry_if_exception_type`을 통해서 재시도하고자 하는 오류를 설정할 수 있다.
  - `stop_after_attempt`는 최대 실행 횟수이고, `wait_exponential_jitter`는 무작위 지연을 설정하는 옵션이다.
  - 전체 체인에 대해서도 재실행 설정이 가능하고, 각 Runnable에 대해서도 따로 재실행 설정을 하는 것이 가능하다.
  - 재시도는 실패 가능성이 있는 좁은 단계에 적용한다.
- LangChain9-2
  - fallback은 보통 실패 후의 대체 방법을 의미한다.
  - `with_fallbacks()`를 통해서 fallback의 등록이 가능하며, 여러 개의 fallback들을 리스트의 형태로 넣을 수 있다.
  - 이 때의 동작은 fallback으로 넘어가면 앞에서부터 순차적으로 동작하게 되며, 가장 먼저 출력되는 값을 전달한다.
  - `exceptions_to_handle`을 통해서 핸들링하고자 하는 오류를 지정하는 것이 가능하며, 그 오류가 발생하여 감지되면 fallback으로 넘어가게 된다.
  - 이 때, fallback의 출력은 primary의 출력을 대체하는 것이 되기 때문에 감안을 하고 primary와 fallback의 출력의 형태를 되도록 같게 해주어야 한다.
  - 다르면 다음 Runnable에서 문제가 발생할 수도 있기 때문에 신경써줘야 한다.
  - 또한 재시도 설정과 fallback설정 전부 래핑하는 것으로 볼 수 있기 때문에 등록하는 순서에 따라서 동작을 다르게 하게 된다.
  - 재시도 설정을 한 다음에 fallback 등록을 하면 재시도를 하고서도 문제가 발생하면 그 때에 fallback으로 넘어가고, 반대의 경우에는 fallback시도도 실패하면 재시도를 하게 된다.
  - graceful degradation은 장애를 숨기지 않고 바로 기능을 전부 다운시키지 않으면서 줄어든 기능과 결과의 한계를 사용자에게 표시하는 방식이다.

## 왜 중요한가
- 오늘 배운 부분은 기초는 아니고 심화에 해당한다고 생각하는데, 쉽지 않은 내용이긴 하다.
- 하지만 트레이싱은 서비스를 운영할 때 필수불가결한 요소이고, 이걸 잘해야지 서비스를 제대로 운영할 수 있다.
- 실제로 나도 서비스를 운영을 해보니까 아무리 작은 서비스더라도 트레이싱이 없어선 운영을 할 수가 없다.
- fallback이나 재시도 같은 장애 대책은 신경쓰지 않으면 서비스 품질을 많이 낮출 수 있는 요소다.
- 그렇기 때문에 중요하다.

```python
# 세션 히스토리 생성 클래스 예제
# session_id와 대화 기록을 연결할 저장소 타입을 정의합니다.
HistoryStore = dict[str, InMemoryChatMessageHistory]


# session_id에 해당하는 대화 기록을 가져오는 함수를 정의합니다.
def get_session_history(
    store: HistoryStore,
    session_id: str,
) -> InMemoryChatMessageHistory:
    """session_id에 해당하는 기록을 가져오고, 없으면 새로 만듭니다."""

    # 처음 들어온 session_id에는 비어 있는 대화 기록을 만들어 저장합니다.
    if session_id not in store:
        store[session_id] = InMemoryChatMessageHistory()

    # 같은 session_id에는 항상 같은 대화 기록을 반환합니다.
    return store[session_id]
```

```python
# fallback 등록 예제
# 일반 함수를 같은 입출력의 Runnable로 바꾸는 클래스를 불러옵니다.
from langchain_core.runnables import RunnableLambda


# 정상 응답을 먼저 시도할 Primary Runnable을 만듭니다.
primary_step = RunnableLambda(primary)
# Primary 장애 뒤 실행할 Fallback Runnable을 만듭니다.
fallback_step = RunnableLambda(fallback)

# 허용한 PrimaryUnavailable만 대체 경로로 보내는 체인을 구성합니다.
resilient_chain = primary_step.with_fallbacks(
    [fallback_step],
    exceptions_to_handle=(PrimaryUnavailable,),
)
```
