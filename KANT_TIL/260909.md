- 딥러닝 심화8-1
  - LLM을 특정 업무에 맞게 맞춰서 사용하기 위해서는 무작정 파인 튜닝을 할 것이 아니라 상황을 파악하고 적절한 방식을 선택해야 한다.
    - prompt only: 모델을 변경하지 않고 입력하는 문장(프롬프트)만 바꾸는 방식
    - prompt tuning: 학습 가능한 soft prompt만 추가로 학습한다.
    - LoRA/PEFT: 작은 adapter 파라미터만 학습
    - full fine-tuning: 모델 전체 파라미터를 업데이트
  - 프롬프트 튜닝은 프롬프트 엔지니어링과 다르게 모델에 입력되는 프롬프트 앞에 학습 가능한 soft prompt 벡터를 붙이고, 이 벡터만을 학습하는 방식이다.
  - 이 때, 추가되는 벡터는 자연어로 표현될 필요 없이 학습이 되는 벡터이다.
  - PEFT는 Parameter-Efficient Fine-Tuning의 약자로 모델 전체를 학습시키지 않고 튜닝을 하는 방식이다.
  - 이는 대체로 모델을 그대로 두고 이외의 작은 조정 장치를 학습 및 관리하는 방식이다.
  - 파인 튜닝 방식을 선택하는 흐름은 다음과 같다.
    - Baseline: prompt-only로 기준 성능 측정
    - 오류 분석: 어떤 유형에서 실패하는지 확인
    - 데이터 확료: 라벨 품질과 수량이 충분한지 확인
    - 학습 선택: PEFT 또는 Fine-tuning 결정
- 딥러닝 심화8-2
  - prompt-only는 보통 baseline으로써 사용되며 학습 없이 어느 정도 해결되는 문제인지 확인할 수 있고, PEFT나 파인 튜닝에서 결과가 얼마나 좋아졌는지 비교하기 위한 기준으로 사용되기 때문에 사용된다.
  - baseline 설계 4요소

| 요소            | 설명                         | 예시                               |
|-----------------|------------------------------|------------------------------------|
| 평가셋          | 모델이 풀어야 할 고정된 샘픔 | 고객 문의 100개                    |
| Prompt template | 모든 샘플에 적용할 입력 형식 | 역할, 라벨 목록, 출력 규칙         |
| Output schema   | 모델이 따라야 하는 출력 형식 | label only 또는 JSON               |
| Metric          | 성능을 판단하는 기준         | Accuracy, Macro-F1, format success |
  - 프롬프트 템플릿 구성 요소
    - Role: 몯레이 어떤 역할로 답할지 설정
    - Task: 분류, 요약, 추출 등 수행할 일
    - Input: 모델이 읽을 실제 데이터
    - Output Schema: JSON, label 표 등 반환 형식
  - prompt-only 베이스라인에서는 모델이 출력 형식을 어기는 일이 흔하다.
  - 따라서 출력 schema를 정하고 모델이 출력을 지켰는지 검사해야 한다.
  - 이런식의 prompt-only 결과는 튜닝 이후에 비교를 위해서 표 형태로 저장해야 한다.
    - prompt_version: 프롬프트의 버전 정보
    - prediction: 모델 출력 라벨
    - gold: 사람이 정한 정답
    - error_type: 틀린 이유에 대한 분류
- 딥러닝 심화8-3
  - 모델의 문제를 해결하는 방법 중 파인 튜닝은 강력하지만 데이터 부족이나 라벨 기준이 불명확해서 생긴 문제에 대해서는 제대로 동작하지 않을 수도 있다.
  - 또한 평가셋이 없다면 모델이 개선되었는지 알 수 없다.
  - 파인 튜닝이 필요한 경우는 다음과 같다.
    - 형식 불안정: 출력 형식이 자주 깨져 후처리가 어렵다.
    - 도메인 용어: 회사만의 분류 기준이나 답변 스타일이 필요
    - 반복 오류: 특정 라벨이나 형식에서 계속 실패
    - 데이터 있음: 검수된 train/valid/test가 있다.
  - 파인 튜닝의 비용은 다음과 같다.
    - 데이터 비용: 수집, 라벨링, 검수, 중복 제거
    - 학습 비용: GPU, 시간, 실험 반복, checkpoint 저장
    - 평가 비용: metric, 오류 분석, 사람 검토
    - 운영 비용: 배포, 모니터링, 버전 관리, 재학습
  - 상황에 따라서 파인튜닝이 유일한 해결책이 아닐 수 있다.
    - 지식 부족: RAG
    - 형식 문제: Prompt, schema검증부터
    - 행동 패턴: 반복되는 스타일, 라벨 판단은 학습 검토
    - 자원 제약: PEFT로 비용을 낮춰 시작
- 딥러닝 심화8-4
  - PEFT의 장점은 전체 모델보다 학습 파라미터 수가 적고, 여러 태스크별 adapter를 따로 저장 및 관리를 할 수 있고, 특정 태스크에 맞춘 조정을 할 수 있다.
  - 단점은 full fine-tuning보다 좋지 않을 수 있고, 어떤 레이어와 모듈에 adapter를 넣을지 결정해야 하고, 병합, 저장, 배포 전략을 관리해야 한다.
  - LoRA는 모델의 특정 Linear layer에 작은 업데이트 경로를 붙이는 방법이다.
  - 모델 자체의 기본 가중치 `W`를 바꾸지 않고, 작은 행렬 두 개를 학습해서 업데이트를 근사한다.
  - 학습을 따로 하지 않고 애초에 `W`를 `W + BA`의 형태로 가중치를 사용해서 역전피를 통해 학습을 진행한다.
  - LoRA에 사용되는 파라미터는 다음과 같다.

| 설정             | 의미                  | 직관                                          |
|------------------|-----------------------|-----------------------------------------------|
| `r`              | LoRA rank             | 작을수록 학습 파라미터가 적다.                |
| `lora_alpha`     | LoRA 업데이트 스케일  | 업데이터 영향력을 조절한다.                   |
| `target_modules` | LoRA를 붙일 몯류 이름 | attention projection 등에 붙이는 경우가 많다. |
| `lora_dropout`    | LoRA 경로의 dropout   | 과적합 완화에 도움을 줄 수 있다.              |
  - PEFT의 방법 선택 기준은 다음과 같다.
    - 데이터 적용: Prompt-only 또는 Prompt tuning부터
    - 성능 필요: LoRA/QLoRA 검토
    - 제약 적음: Full fine-tuning가능
    - 여러 태스크
    - Adapter 교체 운영 고려
- 딥러닝 심화8-5
  - prompt-only와 fine-tuned 모델을 비교할 때에는 반드시 조건을 맞춰서 진행해야 한다.
    - 같은 평가셋
    - 같은 정답 라벨
    - 같은 metric
    - 같은 parsing 규칙
    - 같은 기록 방식
  - 비교에 사용되는 지표
    - Accuracy: 전체 샘플 중 맞힌 비율
    - Macro-F1: 라벨별 F1을 평균한 값
    - Format success: 출력이 요구한 형식을 지킨 비율
    - Latency: 응답까지 걸리는 시간
    - Cost: API 비용, GPU 비용, 운영 비용을 포함
    - Qualitive review: 실제 출력을 사람이 읽고 품질과 위험을 확인
  - 숫자 지표가 좋아지더라도 일부 샘플에 대해서는 성능이 나빠질 수 있다.
  - 이를 regression이라고 한다.
  - 오류 분석 루프
    - 오답 수집: 틀린 샘플을 모은다.
    - 오류 유형화: 형식, 도메인, 모호성, 라벨 문제
    - 원인 판단: Prompt 문제인지 데이터 문제인지 분리
    - 다음 실험: prompt 수정, 데이터 추가, PEFT
  - 비교 리포트에 포함할 항목
    - 문제 정의: 입력, 출력, 라벨 목록, 성공 기준
    - 실험 조건: 모델, prompt 버전, 데이터 split, seed, 후처리 규칙
    - 정량 결과: Accuracy, Macro-F1, format success, latency, 비용
    - 정성 결과: 좋은 예측, 나쁜 예측, 애매한 사례
    - 오류 분석: 오류 유형과 원인
    - 결론: Prompt-only 유지, PEFT 적용, 데이터 보강, Fine-tuning 확대 중 선택
    - 한계: 데이터 크기, 라벨 품질, 최신성, 안정성

  - `max_length`는 입력과 출력을 합친 전체 길이를 제안하고, `max_new_tokens`는 새로 생성되는 토큰의 수를 조절한다.
  - 생성 종료 조건은 다음과 같다.
    - `max_new_tokens`에 도달한다.
    - EOS token이 생성된다.
    - 사용자가 지정한 stopping criteria를 만족한다.
    - 서비스에서 timeout이나 stop string 기준으로 중단한다.

- 딥러닝 심화9-4
  - 일반적인 Causal LM은 입력된 문자열에 대해 이어지는 텍스트를 예측하는거라면 chat model은 대화 형식의 데이터를 학습해서 텍스트의 발화에 대한 정보가 중요하다.
  - chat model은 기본적으로 대화형으로 진행되기 때문에 어떤 텍스트가 누구의 발언인지 구분하기 위해서 텍스트마다 구분하는 토큰을 사용해서 발화자를 확인한다.
  - 이를 위해서 Chat Template를 사용한다.
  - 이 때 구분을 위한 토큰은 모델마다 다르다.
  - 토크나이저의 `apply_chat_template()`는 모델별 대화 문자열로 바꿔준다.
- 딥러닝 심화9-5
  - Chat template의 오류는 대부분 messages 구조에서 잘못된다고 한다.
  - role 이름이 틀리거나 content가 비어있거나 role의 순서를 다르게 적거나
  - `add_generation_prompt=True`는 모델이 다음 assistant 답변을 생성해야 할 시작 위치를 알려주는 형식을 추가하는 옵션이다.
  - 자주 발생하는 오류는 다음과 같다.

| 오류                   | 원인                                            | 해결                                                   |
|------------------------|-------------------------------------------------|--------------------------------------------------------|
| `chat_template`이 없다 | tokenizer에 template이 정의되지 않았다.         | 다른 chat model tokenizer 사용 또는 template 정의 확인 |
| role 오류              | `user`, `assistant`, `system` 외 임의 role 사용 | 모델 문서의 role 규칙 확인                             |
| 출력이 이상하다        | generation prompt 누락 가능성                   | `add_generation_prompt=True` 확인                      |
| token 길이가 너무 길다 | 대화 이력이 과도하게 길어졌다                   | 요약, truncation, history pruning                      |
| 특수 토큰이 중복된다   | 직접 포맷한 문자열에 template을 또 적용했다.    | messages 원본에만 template 적용                        |

```python
# ============================================================
# Prompt-only baseline용 prompt 템플릿 예시
# ============================================================
# 이 코드는 실제 LLM API를 호출하지 않습니다.
# 목적은 모델에 보내기 전 prompt 문자열을 어떻게 일관되게 만들지 확인하는 것입니다.
# prompt도 실험 자산이므로 버전, 라벨 목록, 출력 형식을 함께 기록해야 합니다.

from textwrap import dedent

# 가능한 라벨 목록입니다.
# 모델이 자유롭게 답하지 않도록 label space를 명시합니다.
LABELS = ["refund", "delivery", "account", "other"]

# prompt 버전은 나중에 실험 결과와 함께 저장합니다.
# v1과 v2의 성능이 다를 수 있으므로 prompt 변경 내역을 추적해야 합니다.
PROMPT_VERSION = "prompt_v1_label_only"

# 테스트할 고객 문의 문장입니다.
# 실제 프로젝트에서는 evaluation set의 각 문장을 반복해서 넣습니다.
text = "I paid twice and want my money back."

prompt = dedent(f"""
You are a customer support intent classifier.

Task:
Classify the user's message into exactly one label.

Allowed labels:
{", ".join(LABELS)}

Output rule:
Return only the label. Do not add explanation.

User message:
{text}
""").strip()

print("prompt version:", PROMPT_VERSION)
print(prompt)
```
```python
# ============================================================
# Fine-tuning 적용 조건 점수표
# ============================================================
# 이 코드는 실제 비용을 원 단위로 계산하지 않습니다.
# 목적은 Fine-tuning 전에 준비 상태를 구조적으로 점검하는 것입니다.

import pandas as pd

criteria = [
    {
        "criterion": "문제 정의가 명확한가",
        "description": "입력, 출력, 라벨, 성공 기준이 문서화되어 있는지 확인합니다.",
        "score": 4,
    },
    {
        "criterion": "검수된 데이터가 충분한가",
        "description": "train/valid/test split과 라벨 품질 검수가 되어 있는지 확인합니다.",
        "score": 3,
    },
    {
        "criterion": "Prompt-only baseline이 있는가",
        "description": "학습 전 기준 성능과 오류 유형을 알고 있는지 확인합니다.",
        "score": 5,
    },
    {
        "criterion": "평가 metric이 정해졌는가",
        "description": "Accuracy, Macro-F1, format success 등 개선 기준이 있는지 확인합니다.",
        "score": 4,
    },
    {
        "criterion": "운영 계획이 있는가",
        "description": "저장, 배포, rollback, 모니터링 계획이 있는지 확인합니다.",
        "score": 2,
    },
]

df = pd.DataFrame(criteria)

# 평균 점수는 의사결정의 보조 지표입니다.
# 점수가 낮은 항목은 Fine-tuning 전에 보완해야 할 위험 신호입니다.
average_score = df["score"].mean()

display(df)
```

```python
# ============================================================
# Temperature, Top-k, Top-p 실험표 만들기
# ============================================================
# 같은 prompt에 대해 generation parameter를 바꾸고 결과를 표로 저장합니다.
# 작은 모델은 출력 품질이 낮을 수 있으므로, 여기서는 파라미터 효과 관찰에 집중합니다.

import torch
import pandas as pd
from transformers import AutoModelForCausalLM, AutoTokenizer, set_seed

MODEL_ID = "sshleifer/tiny-gpt2"

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID)
model = AutoModelForCausalLM.from_pretrained(MODEL_ID)

device = torch.device("cuda" if torch.cuda.is_available() else "cpu")
model = model.to(device)
model.eval()

prompt = "In the future, artificial intelligence will"
inputs = tokenizer(prompt, return_tensors="pt")
inputs = {name: tensor.to(device) for name, tensor in inputs.items()}

# 실험할 generation 설정 목록입니다.
# 각 설정은 같은 prompt에 대해 서로 다른 decoding 조건을 의미합니다.
settings = [
    {"name": "low_temperature", "temperature": 0.3, "top_k": 50, "top_p": 1.0},
    {"name": "medium_temperature", "temperature": 0.8, "top_k": 50, "top_p": 1.0},
    {"name": "top_k_10", "temperature": 0.8, "top_k": 10, "top_p": 1.0},
    {"name": "top_p_0_9", "temperature": 0.8, "top_k": 0, "top_p": 0.9},
]

records = []
for config in settings:
    # sampling 결과 비교를 위해 seed를 고정합니다.
    # 실제 운영에서는 여러 seed로 반복 생성해 품질 변동도 보는 것이 좋습니다.
    set_seed(42)

    with torch.no_grad():
        output_ids = model.generate(
            **inputs,
            max_new_tokens=30,
            do_sample=True,
            temperature=config["temperature"],
            top_k=config["top_k"],
            top_p=config["top_p"],
        )

    output_text = tokenizer.decode(output_ids[0], skip_special_tokens=True)
    records.append({
        "setting": config["name"],
        "temperature": config["temperature"],
        "top_k": config["top_k"],
        "top_p": config["top_p"],
        "output": output_text,
    })

result_df = pd.DataFrame(records)
display(result_df)
```
