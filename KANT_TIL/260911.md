| 구분 | 예시                    | 이유                                                          |
|------|-------------------------|---------------------------------------------------------------|
| 고정 | 모델 ID 또는 snapshot   | 모델이 바뀌면 프롬프트 효과와 모델 차이를 구분하기 어렵다.    |
| 고정 | 테스트 입력             | 같은 문제에서 결과를 비교해야 한다.                           |
| 고정 | 평가 루브릭             | 평가 기준이 바뀌면 점수 변화의 의미가 사라진다.               |
| 기록 | Prompt 버전             | 어떤 변경이 성능에 영향을 주었는지 추적한다.                  |
| 기록 | 응답 상태/token/latency | 품질뿐 아니라 운영 비용과 지연시간을 비교한다.                |
| 변경 | 지시문 한 요소          | 변경 원인을 설명할 수 있도록 한 번에 너무 많이 바꾸지 않는다. |
  - 테스트의 기본 흐름은 다음과 같다.
    - Baseline 실행
    - 루브릭으로 평가
    - 실패 원인 가설
    - 프롬프트 한 요소 수정
    - 같은 입력에 재실행
    - 결과와 비용 기록
  - Baseline Prompt는 단순하게 만들어야 한다.
  - 이는 너무 복잡하면 실패 원인을 찾기가 어렵기 때문이다.
  - 복잡한 작업의 프롬프트는 실패 원인을 분석하기 위해서 작업을 나눠서 작성하고 테스트를 한다.
  - 평가 루브릭은 사람마다 다르게 해석되는 기준이 아니라 결과에서 명확하게 확인할 수 있는 행동으로 작성한다.
- 딥러닝 실전 & 프롬프트 엔지니어링6-2
  - Self-consistency란 같은 문제에 대해 여러 후보 답을 만든 뒤, 서로 일치하는 최종 답을 선택하는 방법이다.
  - 전체 파이프라인은 다음과 같다.
    - 문제 입력
      - 여러 후보 생성
      - 최종 답만 파싱
      - 유효하지 않은 후보 제외
      - 투표 또는 점수 기반 선택
  - 다수결이 잘 작동하는 조건

| 조건                             | 적합도    | 이유                                             |
|----------------------------------|-----------|--------------------------------------------------|
| 정답이 하나인 산술/분류 문제     | 높음      | 후보를 같은 형식으로 비교하기 쉽다.              |
| 여러 경로로 풀 수 있는 논리 문제 | 중간~높음 | 서로 다른 경로의 일치가 신뢰 신호가 될 수 있다.  |
| 창의적인 글쓰기                  | 낮음      | 답이 하나가 아니므로 다수결 기준이 부자연스럽다. |
| 최신 사실 질문                   | 낮음      | 모든 후보가 같은 오래된 지식을 사용할 수 있다.   |
| 모호한 요구사항                  | 낮음      | 다수결보다 먼저 요구사항을 명확히 해야한다.      |
  - 후보 다양성을 높이는 방법
    - 동일한 예시만 지나치게 강하게 제시하지 않는다.
    - 후보별로 독립적으로 호출한다.
    - 문제를 다른 표현으로 다시 확인하는 검증 프롬프트를 별도로 둔다.
    - 사실 문제는 검색/데이터베이스/Tool 결과와 대조한다.
  - Reasoning 모델을 사용하는 기준

| 작업                                   | 시작 선택                         |
|----------------------------------------|-----------------------------------|
| 짧은 분류, 단순 추출, 정해진 형식 변환 | 낮은 지연시간의 일반 설정         |
| 여러 제약을 동시에 만족하는 계획       | Reasoning 설정 비교               |
| 복잡한 코드 디버깅                     | Reasoning 설정 비교               |
| 단순 문장 교정                         | 일반 설정                         |
| 중요 의사결정 지원                     | Reasoning + 외부 근거 + 사람 검토 |
  - 모델 선택을 실험으로써 다루기 위해서는 같은 테스트셋, 같은 평가 루브릭 하게 일반 설정/Reasoning effort=low/Reasoning effort=medium을 통해서 품질/지연시간/token을 비교한다.
  - Reasoning 호출 시에는 화면에 보이는 출력 외에 reasoning을 위한 reasoning token이 사용된다.
  - API는 raw reasoning token을 그대로 호출하지는 않아도 사용된 token 수는 알려준다.
- 딥러닝 실전 & 프롬프트 엔지니어링7-1
  - JSON Schema는 모델과 어플리케이션 사이의 출력 계약이다.
  - Structured Output은 모델이 사용자가 지정한 Schema대로 결과를 만들어 반환한다.
  - JSON Schema를 사용하는 이유는 모델이 만들어낸 JSON결과가 JSON 문법을 충족한다고 해서 의도한Schema를 만족하고, 내용이 사실인지 검증하지는 못하기 때문이다.
  - JSON Schema의 핵심 키워드는 다음과 같다.
    - type: 문자열, 숫자, 객체, 배열처럼 값의 자료형을 정한다.
    - properties: 객체 안에 허용할 필드를 정의한다.
    - required: 반드시 있어야 하는 필드를 지정한다.
    - enum: 허용 가능한 값의 목록을 제한한다.
    - items: 배열 안 원소의 구조를 정의한다.
    - additionalProperties: 정의하지 않은 필드를 허용할지 결정한다.
  - 출력 계약을 설계하는 순서
    - 출력이 사용될 위치를 정한다.
    - 최소 필드를 고른다.
    - 각 필드의 자료형과 허용값을 정한다.
    - 정보가 없을 때의 정책을 정한다.
- 딥러닝 실전 & 프롬프트 엔지니어링7-2
  - `Pydantic`은 파이썬 타입 힌트를 바탕으로 입력 데이터를 검증하고 파이썬 객체로 변한해주는 라이브러리이다.
  - 자료형이 맞지 않아 검증에 실패하면 `ValidationError`를 발생시킨다.
  - Pydantic 검증의 흐름
    - Pydantic 모델 정의
      - JSON Schema 생성
      - 모델에 출력 구조 전달
      - 구조화된 응답 수신
      - Pydantic 객체로 파싱
      - 비즈니스 규칙 검증
      - 저장/Tool/UI에 전달
  - OpenAI Python SDK에서는 `responses.parse()`를 통해서 Pydantic 모델을 `text_format`으로 전달하고, 파싱된 결과를 `response.output_parsed`에서 읽을 수 있게 만들어준다.
  - 정의되지 않은 임의의 필드를 막기 위해서는 `extra="forbid"`를 사용하면 된다.
  - `Literal`은 `enum`과 비슷한 역할을 한다.
  - Pydantic은 편의를 위해서 일부 값을 자동으로 변환해준다.
  - strict는 그런 변환 없이 엄격하게 잘형을 검사한다.
  - pydantic으로 생성한 객체의 `model_json_schema()`를 통해서 JSON Schema를 생성할 수 있다.

- 딥러닝 실전 & 프롬프트 엔지니어링8-1
  - Function Calling은 모델이 애플리케이션에 등록된 도구 중 어떤 도구를 사용할지 선택하고, 그 도구에 필요한 인자를 구조화해 반환하도록 하는 기능이다.
  - Tool Schema 구성요소
    - `name`: 도구 이름
    - `description`: 언제 사용하고 언제 사용하지 않는지에 대한 설명
    - `parameters`: JSON Schema로 인자의 타입과 제약을 정한다.
    - `required`: 함수 실행에 꼭 필요한 필드
    - `strict`: Schema 준수 강화
    - `tool_choice`: 모델의 도구 선택 범위를 제어
  - Tool Calling의 단계
    - 도구 목록과 요청
    - function_call 수신
    - 인자 검증, 함수 실행
    - function_call_output 전달
    - 최종 응답
  - function calling에서 1차 모델 응답과 2차 모델 응답이 나뉜다.
  - 1차 모델 응답은 어떤 모델을 사용할지에 대한 function call이다.
  - 2차 모델은 도구 결과를 이용한 최종 자연어 답변이다.
  - Tool Calling은 실행 경계가 있으며 모델과 애플리케이션 간의 책임이 분리된다.
    - 모델: 사용할 Tool과 arguments를 제안한다.
    - 애플리케이션: JSON 파싱, Pydantic 검증, 권한, 업무 규칙 확인을 수행
    - 외부 시스템: 검증을 통과한 요청만 실제로 실행
  - strict Schema 작성 규칙
    - parameters.type은 object
    - properties의 모든 필드를 required에 포함
    - additionalProperties는 false
    - Tool 수준의 strict는 true
    - 선택 의미가 필요하면 null을 타입에 포함
  - tool_choice와 parallel tool call에 따라서 모델은 기본적으로 도구를 호출할지 판단한다.

| 설정           | 동작                                         |
|----------------|----------------------------------------------|
| "auto"         | 도구를 0개, 1개 또는 여러 개 선택할 수 있다. |
| "required"     | 하나 이상의 도구 호출을 요구한다.            |
| 특정 함수 지정 | 지정한 함수를 정확히 한 번 호출하게 한다.    |
| "none"          | 도구를 사용하지 않게 한다.                   |
  - function_call item 해석

| 필드        | 의미                      | 애플리케이션에서 할 일                            |
|-------------|---------------------------|---------------------------------------------------|
| `type`      | item 종류                 | `function_call`인지 먼저 확인한다.                |
| `name`      | 모델이 선택한 Tool 이름   | allowlist router에 등록된 이름인지 확인한다.      |
| `arguments` | JSON 문자열               | `json.loads()`후 Pydantic으로 검증한다.           |
| `call_id`    | 호출과 결과를 연결하는 ID | `function_call_output_call_id`에 그대로 사용한다. |
- 딥러닝 실전 & 프롬프트 엔지니어링8-2
  - 모델이 strict Schema를 따르더라도 애플리케이션은 실행 경계에서 다시 검증해얌나 한다.
  - 다음 항목을 별도로 확인해야 한다.
    - JSON 문자열이 파싱되는가?
    - arguments field와 자료형이 맞는가?
    - 문자열 형식과 숫자 범위가 맞는가?
    - 호출할 함수 이름이 allowlist에 있는가?
    - 현재 사용자가 실행 권한을 가지고 있는가?
    - 같은 부작용 요청이 중복 실행되지 않는가?
  - 안전한 함수 실행의 흐름은 다음과 같다.
    - function_call item
      - name 확인
      - arguments JSON 파싱
      - Pydantic  검증
      - 권한/업무 규칙 확인
      - allowlist router에서 함수 선택
      - 함수 실행
      - 성공/실패 결과 생성
      - function_call_output 준비
  - eval을 통한 함수 실행은 절대로 해서는 안된다.
  - Tool Calling의 실행 경계 및 검증

| 검증 층   | 확인 내용                                  | 실패 시 처리                       |
|-----------|--------------------------------------------|------------------------------------|
| JSON 파싱 | 문자열이 올바른 JSON 인가?                 | 함수 실행 없이 오류를 반환한다.    |
| Pydantic  | 타입, 필수 필드, 허용 범위가 맞나?         | `ValidationError`를 기록한다.      |
| 업무 규칙 | 주분 ID 형식, 금액 한도, 현재 상태가 맞나? | 업무 오류로 분류한다.              |
| 권한/승인 | 현재 사용자가 이 작업을 수행할 수 있나?    | 거부하거나 사용자 확인을 요청한다. |
- 딥러닝 실전 & 프롬프트 엔지니어링8-3
  - 모델이 선택한 Tool을 실행한 뒤에는 모델로 결과를 보내서 후처리를 해야한다.
  - Tool Calling 상태 전이 및 재시도 정책

|실패 위치|대표 원인|권장 처리|
|---|---|---|
|모델 응답|Tool Call이 없음|Tool이 꼭 필요한 요청인지 다시 판단한다.|
|JSON/Pydantic 검증|누락 필드, 잘못된 타입|함수는 실행하지 않고 수정 요청 또는 종료한다.|
|업무 검증|주문 없음, 권한 없음|재시도보다 사용자 안내가 우선입니다.|
|외부 합수 실행|timeout, 일시적 5xx|횟수 제한과 backoff를 적용한다.|
|최종 응답|응답 incomplete|Tool 결과는 보존하고 최종 설명만 재생성할 수 있다.|
  - function_call_output 구성
    - `type`: "function_call_output"
    - `call_id`: 1차 응답 function call과 같은 `call_id`
    - `output`: 실행 결과 문자열
  - Tool 결과 왕복 흐름
    - 사용자 질문
      - 1차 Response 호출
      - function_call 수신
      - arguments 검증
      - 실제 함수 실행
      - function_call_output 추가
      - 2차 Response 호출
      - 최종 사용자 응답
  - 조회용 Tool과 부작용 Tool의 안전장치는 서로 다르다.
    - 실행 직전의 사용자 확인
    - 권한과 금액 한도 검증
    - 중복 실행을 막는 idempotency key
    - 실행 전후 상태와 request ID를 남기는 audit log
    - timeout 뒤 실제 실행 여부를 확인하는 조회 단계
  - Tool loop에는 종료 조건이 필요하다.
    - 최대 반복 횟수
    - 허용 Tool 목록
    - 동일 call 반복 감지
    - 총 지연시간 제한
    - 총 token/비용 제한
    - 사용자 확인이 필요한 지점
